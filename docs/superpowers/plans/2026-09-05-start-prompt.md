## Что делать

Выполняй планы строго по порядку: сервер → клиент → дистрибуция. Каждый план целиком через `superpowers:subagent-driven-development`: свежий имплементатор на задачу, task review после каждой задачи, финальное whole-branch review в конце плана, затем `superpowers:finishing-a-development-branch`. Следующий план начинай только после того, как финальное review предыдущего чистое и ветка влита в `main`. Между задачами не спрашивай меня и не пиши сводки прогресса; ledger ведёшь в `.superpowers/sdd/<plan-basename>/progress.md`, как требует скилл.

Ветки и worktree: на каждый план создай отдельный worktree через `superpowers:using-git-worktrees` от актуального `main`: ветки `v0.1-server`, `v0.1-client`, `v0.1-distribution`. Даю явное согласие на это и на локальный merge каждой готовой ветки в `main` (fast-forward или merge-коммит, без rebase истории). Push в remote и любая публикация в npm запрещены без моего отдельного «да».

## Выбор модели для субагентов

Указывай модель явно в каждом диспатче. Уровни: `sonnet` — дешёвый, `opus` — стандартный, `fable` — самый сильный. `haiku` не использовать: задачи многошаговые, он выигрывает в цене и проигрывает в числе ходов.

Имплементаторы:

| Уровень | Задачи |
|---|---|
| `sonnet` | сервер 2, 3, 5, 6, 7, 8, 9, 11, 12, 16; клиент 1, 2, 7; дистрибуция 1, 3 |
| `opus` | сервер 1, 4, 10, 13, 14, 15, 17; клиент 3, 4, 5, 6, 8, 9, 10; дистрибуция 2 |

Правило за таблицей: в тексте задачи уже есть полный код и тесты, поэтому одиночные чистые модули идут на `sonnet`; всё, где есть e2e, middleware, Nuxt UI, Nuxt-runtime-тесты, роутер, tarball или сборка, идёт на `opus`.

Ревью: task reviewer — `opus`; scoped re-review небольшого fix-диффа — `sonnet`; финальное whole-branch review каждого плана — `fable`. Эскалация в fix-раундах 4–5: `sonnet` → `opus`, `opus` → `fable`.

## Правила для всех субагентов

- Факты о Nuxt 4 и Nuxt UI 4 брать из MCP-серверов `nuxt` и `nuxt-ui` или из спеки §16, не из памяти модели. Если поведение фреймворка расходится с планом, сначала проверить в MCP, потом править.
- Автотесты — единственные ворота задачи. Шаги плана «открой приложение и посмотри» субагент выполняет только если может управлять браузером; иначе пропускает, а ты помечаешь это в ledger. Ручной smoke pass из задачи 10 клиентского плана делаю я сам: после финального review клиентского плана остановись и попроси меня его пройти.
- Один коммит на задачу, conventional commits, в теле `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- Если `pnpm install` сообщает об игнорируемых build-скриптах зависимостей, выполнить `pnpm approve-builds`, одобрить их и продолжить; это не дефект плана.
- Код, идентификаторы и комментарии — на английском; со мной общайся по-русски.

## Где остановиться

Только четыре случая из скилла: необратимая или разрушительная операция; действие, затрагивающее безопасность; побочный эффект вне worktree, кроме заранее разрешённого локального merge; план, где любой путь вперёд — угадывание. Плюс два названных выше: smoke pass после клиентского плана и `npm publish` в задаче 3 плана дистрибуции.

Начинай с серверного плана: создай worktree, прочитай план и спеку, сделай pre-flight scan по скиллу, заведи ledger и диспатчь задачу 1 на `opus`.
